# 文章点赞乐观状态统一设计

## 目标

修复以下文章点赞状态不同步问题：

- 列表点赞数字变化后，图标与文字没有立即进入激活色。
- 详情左侧点赞数字和激活态都不能立即更新。
- 列表与详情之间切换时，点赞数字和激活态可能来自不同状态源。

交互采用乐观更新：用户点击后立即更新数字与激活态；请求失败时恢复原状态。

## 根因

文章列表与详情正文已经由 TanStack Query 管理，但详情点赞仍写入 Pinia 中的文章镜像和点赞 ID 列表。界面读取的对象与点赞操作写入的对象不同：

- 列表文章与点赞态读取 TanStack Query 缓存。
- 详情文章读取详情 Query 缓存。
- 详情点赞操作写入 Pinia，并异步重新请求点赞 ID。

因此接口成功不等于当前界面使用的响应式数据已经同步。仅失效查询还会让视觉反馈依赖后续网络请求，无法保证即时激活。

## 方案

以 TanStack Query 作为文章服务端状态的单一来源，并由 `useLikeArticle` 统一负责文章点赞事务。

### Query key

在 `articleKeys` 中增加统一的详情 key：

- `articleKeys.lists()`：全部文章列表缓存。
- `articleKeys.detail(articleId)`：指定文章详情缓存。
- `articleKeys.userLiked(userId)`：当前用户点赞过的文章 ID。

`useArticleDetail` 使用该 key，避免点赞逻辑拼接匿名数组 key。

### 乐观更新事务

`useLikeArticle` 在发起请求前：

1. 取消文章列表、当前详情和当前用户点赞查询，防止旧请求覆盖乐观值。
2. 保存上述缓存快照。
3. 从点赞 ID 缓存判断点击前是否已点赞。
4. 立即切换点赞 ID，并将目标文章点赞数加一或减一；最小值保持为零。
5. 同步修改所有已缓存列表页以及目标详情缓存。

请求成功后，使用接口返回的 `liked` 和 `likes` 精确校准三类缓存并显示成功/取消提示。请求失败时恢复完整快照并显示失败提示。结束后失效相关查询，在后台确认服务端最终状态。

同一篇文章的 mutation 未结束时，交互入口不再提交第二次请求，避免快速连点造成多个乐观事务互相覆盖。

## 组件数据流

- `ArticleAction` 保持展示组件职责：接收文章、`isLiked` 与点赞回调。
- `DetailPanel` 改为使用 `useUserLikedArticles` 和 `useLikeArticle`，不再调用 Pinia 的 `likeAction`。
- `useArticleDetail` 不再为了详情点赞触发 Pinia 点赞 ID 请求；Pinia 中仍被旧流程使用的代码不在本次做无关清理。
- `Icon` 已支持 `isActive` 对图标和文字统一着色，不需要引入额外样式状态。

## 错误与边界处理

- 未登录与封禁文章仍沿用现有提示和登录弹窗行为。
- 点赞 ID 统一转为数字，规避接口返回字符串 ID 时严格比较失败。
- 缓存中暂时没有点赞 ID 数据时，以未点赞作为乐观起点，并由成功响应校准。
- 数字缺失时按零处理，取消点赞不会产生负数。
- 非零业务响应按失败处理，不能提交错误的成功状态。

## 测试

先增加会失败的回归测试，再编写实现：

1. 点赞前立即更新全部列表缓存、详情缓存和点赞 ID 缓存。
2. 取消点赞立即减数并移除激活态。
3. 接口成功后以服务端 `liked/likes` 校准乐观值。
4. 请求失败后完整回滚三类缓存。
5. 详情面板使用统一 composable，不再调用 Pinia 点赞 action。
6. 运行相关 Vitest、全量类型检查与生产构建。

## 非目标

- 不迁移评论点赞逻辑。
- 不重写文章分页、搜索或标签逻辑。
- 不删除 Pinia 中仍可能被旧页面调用的文章读取状态。
- 不修改点赞接口协议；继续使用 `{ code, data: { liked, likes } }`。
