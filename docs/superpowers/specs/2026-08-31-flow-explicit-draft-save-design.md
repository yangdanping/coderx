# Flow 显式草稿保存与退出确认设计

日期：2026-08-31

## 背景

Flow 编辑器当前会在文本或图片变化后立即写入本地草稿，并在登录态下以 1.2 秒防抖自动同步到服务器。这个行为与文章编辑器一致，但不适合更轻量的 Flow 发布场景：用户只是在临时输入并退出时，也可能留下并不想保留的服务器草稿。

本次只调整 Flow。文章编辑器的自动保存行为保持不变。

## 目标

- 取消 Flow 编辑过程中的自动草稿持久化。
- 将“保存草稿”改为用户主动选择的动作。
- 发布按钮旁显示“保存草稿”按钮；仅当存在文本或图片且当前有未保存变更时可用。
- 退出时仅对未保存的有意义内容提示“保存草稿”或“放弃”。
- 已保存且未再修改时直接退出，不重复提示。
- 已保存后继续修改时，放弃修改只回退到上一版已保存草稿，不删除服务器草稿。
- 避免未保存图片长期占用服务端资源。

## 非目标

- 不修改文章编辑器草稿逻辑。
- 不修改 Flow 草稿接口结构。
- 不增加草稿列表、草稿命名或多草稿能力。
- 不把未保存内容写入 localStorage；刷新页面与浏览器崩溃恢复不在本次范围内。

## 方案比较

### 方案 A：显式保存状态机（采用）

草稿 composable 负责恢复、显式保存、清空以及保存基线；页面负责当前编辑态和退出编排。编辑变化只更新内存和 `dirty` 状态，不触发本地或远程持久化。

优点是状态语义清晰、请求边界集中，能够可靠地区分“当前内容”“上一版已保存内容”和“未保存变更”。代价是需要调整现有自动保存 composable 及相关测试。

### 方案 B：保留调度器但禁用定时触发

继续沿用自动保存调度器，只在点击按钮时调用 flush。

改动看似较小，但 `dirty`、本地 fallback 和队列语义仍然围绕自动保存设计，容易出现点击放弃后队列继续保存或空内容生成 fallback 的隐患，因此不采用。

### 方案 C：页面组件直接调用草稿接口

由 `Flow.vue` 在点击按钮或退出确认后直接发送保存请求。

实现直接，但会让恢复、版本冲突、本地 fallback 和请求错误处理分散到页面组件，破坏现有层次，也更难测试，因此不采用。

## 状态模型

系统同时维护两份概念状态：

- `currentSnapshot`：编辑器当前的结构化文本和图片 ID，仅驻留页面内存。
- `savedBaseline`：初始化恢复或最近一次成功保存后的快照与图片描述符。

派生状态：

- `hasContent`：当前结构化文档包含非空白文本，或当前保留至少一张图片。
- `isDirty`：`currentSnapshot` 与 `savedBaseline` 不一致。图片按当前顺序比较 ID；文本比较规范化后的 Tiptap JSON。
- `canSave`：`hasContent && isDirty`，并且未处于恢复、保存、发布、清空、图片上传或图片恢复不完整等锁定状态。
- `shouldConfirmClose`：`hasContent && isDirty`。

初始化没有远端或本地草稿时，基线为空快照。恢复已有草稿时，恢复内容同时成为保存基线，因此打开后不显示为未保存。

## 交互流程

### 主操作区

“保存草稿”放在“发布”按钮左侧，作为次要按钮；发布保持主按钮。

- 空内容：保存草稿按钮禁用。
- 有内容但与已保存基线相同：保存草稿按钮禁用。
- 有未保存内容：保存草稿按钮启用。
- 保存中：按钮显示“保存中…”，编辑、退出和发布按现有生命周期规则锁定。
- 保存成功：更新保存基线，状态提示为“已保存”，按钮恢复禁用。
- 保存失败：编辑器保持打开，当前内容和图片保留，显示失败提示，可重试。

清空草稿入口保留，继续承担“明确删除已保存草稿”的职责；它与退出时的“放弃修改”不是同一动作。

### 退出

关闭按钮和 Escape 共用同一退出流程。

1. 当前无未保存的有意义内容：直接关闭。
2. 当前有未保存内容：显示三态确认框。
   - “保存草稿”：执行显式保存；成功后关闭，失败则保持编辑器打开。
   - “放弃”：不保存当前变更，恢复到 `savedBaseline` 后关闭。
   - “取消”：关闭确认框，继续编辑。
3. 新建且从未保存的内容选择“放弃”时，基线为空，因此关闭后重置为空编辑器。
4. 已保存草稿又被修改时选择“放弃”，恢复上一版已保存内容，远端草稿保持不变。

确认文案采用“保存草稿 / 放弃 / 取消”，标题为“退出 Flow 编辑？”，正文说明存在尚未保存的内容。

### 发布

发布仍直接使用当前内容，不要求先保存草稿。发布成功后沿用现有流程清理本地 fallback 和远端草稿，并重置编辑器。

## 图片生命周期

图片上传仍在选择文件后立即发生，因此“放弃”需要处理尚未属于已保存基线的图片：

- 比较当前图片 ID 与 `savedBaseline` 图片 ID。
- 放弃时仅删除当前新增、未进入基线的图片。
- 基线中已有的图片不能因为放弃本轮修改而删除。
- 如果新增图片删除失败，仍允许关闭，并提示图片将由服务端自动回收。
- 保存成功后，当前图片集合成为新基线，不再视为待放弃附件。
- 用户显式删除一张已保存图片但随后放弃修改时，应重新恢复基线中的图片描述符与顺序。

## 组件边界

### `useFlowDraftAutosave`

保留文件名以降低调用面变更，但职责改为 Flow 草稿持久化控制器：

- 初始化并恢复最后一次显式保存的草稿。
- 记录当前内存快照并计算 dirty，不安排自动保存。
- 暴露 `saveDraft()`，显式写本地 fallback 和服务器。
- 暴露保存基线及恢复基线所需状态。
- 保留清空与发布后重置能力。
- 版本冲突和恢复失败继续使用现有错误状态。

### `Flow.vue`

- 汇总当前文档、图片和媒体 ID 为快照。
- 编排保存按钮、退出确认、放弃回退、发布后重置。
- 对 Element Plus 确认框的三个结果分别处理。
- 保持恢复失败和图片不完整时的安全锁定规则。

### `FlowEditorModal.vue`

- 渲染保存草稿按钮并发出 `save-draft` 事件。
- 将所有关闭入口继续收敛为 `close` 事件，由页面决定是否确认。
- 不直接调用草稿接口或确认框。

## 错误与并发处理

- 保存期间锁定重复保存、退出、发布和清空，避免同一版本并发请求。
- 保存请求发生 409 时保留当前内容并显示冲突，不更新基线。
- 退出选择保存但请求失败时，不关闭编辑器。
- 恢复失败时保持现有策略：允许继续输入，但禁止保存、发布和清空，避免覆盖未知远端草稿。
- 图片仍在上传或恢复不完整时禁止保存；退出提示保留，选择放弃可回退或清空当前内存内容。
- 不在 `beforeunload` 中发网络请求；本次退出确认仅覆盖 Flow 编辑器内的关闭按钮和 Escape。

## 测试策略

按照 TDD 先增加失败测试，再实现：

1. composable：编辑变化不写 localStorage、不调用保存接口；显式保存才持久化并更新基线。
2. composable：空白文本不算内容；图片单独存在时算内容。
3. modal：保存按钮位于发布按钮旁，按 `canSave` 启停并发出保存事件。
4. page：无 dirty 直接关闭；新内容退出显示三态确认。
5. page：退出选择保存时成功后关闭，失败时保持打开。
6. page：退出选择放弃时，新内容清空；已有草稿的修改回退到基线且不删除远端草稿。
7. page/image queue：放弃只清理相对基线新增的图片，保留已保存图片；删除失败给出回收提示。
8. 回归：发布、草稿恢复、版本冲突、恢复失败和清空草稿现有测试继续通过。

完成后运行 Flow 定向测试、类型检查，并在风险允许时运行完整测试与构建。
