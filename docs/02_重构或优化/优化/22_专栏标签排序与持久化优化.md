# 专栏标签排序与持久化优化总结

> 更新时间：2026-07-12

## 1. 优化目标

文章专栏的标签导航原本只支持固定顺序。本次优化允许用户调整“综合”之外的标签顺序，同时兼顾桌面端、移动端、游客和登录用户。

核心原则：

- “综合”是固定入口，不参与排序，也不会写入缓存或数据库。
- 桌面端通过显式编辑模式整行拖拽，默认状态不展示拖拽手柄。
- 移动端在底部抽屉中纵向排序，避免横向滚动和拖拽手势冲突。
- 拖拽后立即乐观更新；保存失败则恢复到最后一次成功保存的顺序。
- 游客保存在本机，登录用户保存在服务端。

## 2. 交互优化

### 桌面端

“综合”右侧提供排序设置入口。进入编辑模式后，除“综合”外的标签整行可拖；再次点击关闭按钮或点击导航区域外即可退出。

进入编辑状态时只有一次短暂的位移提示，不使用持续抖动，并兼容 `prefers-reduced-motion`。

### 移动端

顶部标签仍保持单行横向滚动，默认不显示 Grip。点击右侧排序按钮后打开底部抽屉：

- “综合”显示为固定项。
- 其他标签通过右侧手柄纵向拖动。
- 标签行、完成按钮和手柄保持约 44px 的触控尺寸。
- 抽屉使用 `append-to-body`，确保始终相对视口底部定位。

## 3. 保存链路

```text
拖拽完成
  → 前端立即更新顺序
  → 根据认证状态选择保存位置
      ├─ 游客：localStorage
      └─ 登录用户：PUT /tag/order
  → 成功：更新 committed 顺序
  → 失败：回滚 committed 顺序并提示用户
```

`useTagOrder` 同时维护：

- `orderedTags`：当前界面显示的乐观顺序。
- `committedTags`：最后一次确认保存成功的顺序。
- `isSaving`：保存锁，防止前一次请求未完成时重复提交拖拽。

## 4. 游客保存策略

游客顺序保存在：

```text
localStorage["coderx_guest_tag_order"]
```

缓存只保存标签 ID，不保存标签名称或完整对象。每次读取时都会：

1. 过滤非正整数、重复 ID 和已经删除的标签。
2. 按缓存顺序排列仍然存在的标签。
3. 将服务端后来新增的标签按默认顺序追加到末尾。

这样即使后台新增或删除标签，旧缓存也不会导致导航缺项或请求失败。

## 5. 登录用户保存策略

登录用户通过以下接口保存完整顺序：

```http
GET /tag/order
PUT /tag/order

{
  "tagIds": [3, 1, 2]
}
```

服务端不会接收客户端传入的 `user_id`，而是从 JWT 鉴权结果中取得当前用户 ID。

`PUT /tag/order` 使用事务执行完整替换：

1. 校验参数必须是无重复的正整数数组。
2. 校验所有标签 ID 当前都存在。
3. 删除该用户原有偏好行。
4. 按数组下标写入新的 `sort_order`。
5. 任一步失败则回滚整个事务。

## 6. 游客登录后的冲突解决

当游客调整过顺序后再登录，可能同时存在“本机游客顺序”和“账号云端顺序”。当前采用以下规则：

| 场景 | 处理方式 |
| --- | --- |
| 本机没有游客顺序 | 保留并加载账号云端顺序 |
| 本机存在游客顺序 | 本机顺序优先，一次性覆盖账号云端顺序 |
| 本地包含已删除标签 | 删除失效 ID 后再同步 |
| 服务端出现新标签 | 追加到本地顺序末尾后再同步完整列表 |
| 同步成功 | 清除游客缓存，后续完全使用账号云端顺序 |
| 同步失败 | 保留游客缓存、保留原云端顺序并提示用户，下次登录继续尝试 |

普通账号登录和 OAuth 登录都会在刷新或跳转前等待迁移结束，避免请求被页面导航中断。

这套规则的取舍是：用户刚在当前设备调整的顺序，被认为比账号旧顺序更新。如果以后需要“云端优先”或弹窗询问，只需要替换登录迁移策略，不需要修改表结构。

## 7. 数据库设计

排序没有放到全局 `tag` 表，因为同一个标签对不同用户可能处于不同位置。当前使用独立关系表：

```text
user_tag_preference
├── user_id      bigint      用户 ID
├── tag_id       bigint      标签 ID
├── sort_order   integer     从 0 开始的用户内顺序
└── updated_at   timestamptz 最后更新时间
```

关键约束与索引：

- 主键 `(user_id, tag_id)`：同一用户不能重复保存同一标签。
- 唯一约束 `(user_id, sort_order)`：同一用户的两个标签不能占据同一位置。
- `CHECK (sort_order >= 0)`：禁止负数顺序。
- 两个外键均使用级联更新、删除。
- 单独为 `tag_id` 建索引，避免删除标签时扫描整张偏好表。

迁移脚本：`../coderx_server/migrations/007_create_user_tag_preference.sql`。

## 8. 失败与恢复策略

| 失败位置 | 恢复方式 |
| --- | --- |
| 浏览器本地写入失败 | 前端恢复最后一次 committed 顺序 |
| `PUT /tag/order` 网络或业务失败 | 前端恢复原顺序并显示“顺序保存失败” |
| 服务端写入中途失败 | PostgreSQL 事务回滚，原顺序不变 |
| 登录迁移失败 | 不清游客缓存，不阻断登录，后续登录重试 |
| 个性化顺序读取失败 | 回退到公共标签默认顺序 |

## 10. 后续维护注意事项

- 新增标签时不需要批量更新所有用户偏好；查询和合并逻辑会自动追加。
- 不要将“综合”伪造为标签 ID 写入保存数组。
- 不要给 `tag` 表增加全局 `sort_order`，否则无法表达用户个性化顺序。
- 如果修改完整替换接口，必须继续保持事务和失败回滚语义。
